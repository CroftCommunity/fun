# Making fun.croft.ing installable — per game, and as a shelf

status: **Pass 1 (shape).** Not started. No blocking open questions; three defaults recorded below.

**owner decision (2026-08-09):** nested scope — *"separate when installed isolated, together when
installed at the top level"* — **conditional on it working**. That condition is not rhetorical; it
maps onto a specific unverified spec behaviour, so Phase 1 is a **gate** that can stop the plan.

## Problem Statement

`fun.croft.ing` is a games shelf of **20 static pages** that looks like an app and is not one.
Verified 2026-08-09: there is **no `*.webmanifest`, no `manifest*.json`, no `rel="manifest"`, and no
`serviceWorker` registration anywhere in the repo** — not in `src/`, not in `build.mjs`, not in
`dist/`. It is not installable, has no offline story, and no app identity.

The owner wants two things at once:

1. Each game at `/<game>/` installable **on its own** — solitaire as an app on the home screen.
2. The **whole shelf** installable as one app.

These are in tension because a page links **exactly one manifest**. There is no API for site UI to
offer a choice, so *where the user presses install* is the entire selection mechanism. Two manifests
whose scopes nest (`/` containing `/solitaire/`) is the configuration Chromium rates worst.

The question is therefore not "can we" — mechanically yes — but **does the isolation the owner asked
for actually hold**, and what breaks when it does not.

## Approach

Ship a manifest per page plus one service worker, generated by the build, and **gate the rollout on
proving install isolation before doing it 20 times**.

```
/manifest.webmanifest              id "/"            scope "/"            the shelf
/solitaire/manifest.webmanifest    id "/solitaire/"  scope "/solitaire/"  one game
/wyrdle/manifest.webmanifest       id "/wyrdle/"     scope "/wyrdle/"     one game
        …                                                                 (18 more)
```

`build.mjs` already emits every page through a **single `page()` template function** (`build.mjs:26`)
driven by one `GAME_PAGES` array (`build.mjs:16`). So the `<link rel="manifest">` injection and the
manifest generation are **one function and one loop**, not 20 edits.

**Paths are absolute (`"/"`, `"/solitaire/"`), matching the rest of the repo.** This is a deliberate
departure from croft-pwa's relative-path rule, and the reasoning is recorded because it looks like a
violation and is not: croft-pwa requires relative paths so one build runs at a domain root *and*
under a subpath, because it genuinely deploys both ways (a project page at `/croft-pwa/`, and
`/pr-preview/pr-N/`). **`fun` has neither** — one workflow, no preview job, `CNAME` = `fun.croft.ing`,
only ever a domain root — and every page it already emits uses `base: "/"` (`build.mjs:243`;
`dist/solitaire/index.html` links `href="/styles.css"`). Matching the repo beats importing a rule
whose justification is absent here. **If `fun` ever gains a subpath deploy, the existing absolute
asset paths break first** and the manifest is the least of it; that is the trigger to revisit, and it
is a bigger change than this plan.

## Reasoning

**Why the gate comes first.** The owner's requirement rests on one claim from the source dialogue:
*"distinct `id` values keep the installs separate."* That claim is **unverified and load-bearing**.
Per the manifest spec, `id` resolves against the **origin** — unlike `start_url` and `scope`, which
resolve against the manifest URL. So the mental model "each manifest sits in its directory and
therefore gets its own identity" is not obviously how `id` behaves, and it is the exact property the
owner conditioned on. Guessing costs 20 manifests, a service-worker scope decision, and a rollback;
**measuring costs one build and two installs.** So Phase 1 ships exactly two manifests and answers
it.

**Why nested scope is acceptable even when Chromium misbehaves.** The known symptom is that with the
shelf installed and a game not, `/solitaire/` links do not capture into a solitaire app and open in
the shelf instead. For a shelf that *contains* the games, opening solitaire inside the shelf app is
odd but not broken. Worth being precise that this is **Chromium's deployment choice, not the
manifest spec** — Safari (iOS/macOS) and Firefox have no install prompt and no link capturing at all,
so on those the either/or resolves by construction: whichever page you were on is what you installed.
The blast radius of being wrong is one browser family, degrading to "the game opens in the shelf."

**Why a service worker at all, when the ask was install.** Chromium will not offer install without a
fetch handler, so offline is not an optional extra here — it is part of the entry price. It is also
the larger share of the actual value: 20 static games that work on a plane.

**Why one service worker and not one per game.** A SW's scope is capped by its own path, so per-game
workers would each need to sit at `/<game>/sw.js`, giving 20 registrations, 20 caches, and 20 update
cycles for one shared `app.js`. One worker at `/sw.js` covers every page and caches the shared bundle
once. The cost is that an installed *game* app carries a worker whose scope is wider than its
manifest scope — which is legal, and matters only if we later want per-game cache eviction. Recorded
as a known asymmetry rather than discovered later.

**Why the icons question is real work and not a footnote.** Twenty installable apps need twenty
distinguishable icons, or the home screen becomes a row of identical tiles and the whole feature is
pointless. The shelf has per-game art already; whether it is usable at maskable-icon sizes is
unverified and is Phase 2's first task, not an assumption.

## Phases

**Phase 0 — the service worker, no install yet.** `src/sw.ts` with the routing decision as a **pure,
unit-tested function** separate from the worker runtime (croft-pwa's `sw-nav.ts` pattern:
non-GET → skip; navigations → network-first; same-origin hashed assets → cache-first; cross-origin →
never `respondWith`). Registration failure is swallowed — offline is progressive enhancement, and a
SW bug must not blank the shelf. RED first on the routing function. No manifest in this phase, so it
is independently revertable and ships value alone.

**Phase 1 — TWO manifests, and the gate.** Shelf + solitaire only. Install both on Chromium, confirm
they appear as **two separate apps** with correct names and icons, and record the result in the plan.

- **If separate:** proceed to Phase 2.
- **If they collapse into one install:** stop. Fall back to the recorded alternative —
  `solitaire.fun.croft.ing`-style subdomains, so no scope contains another — and re-plan, because
  that changes DNS, deploy, and the share-URL story. **Do not proceed to 20 manifests on a hope.**

**Phase 2 — icons.** Audit the 20 games' existing art at 192/512 + maskable. Generate what is
missing. This is the phase most likely to be larger than it looks, and it is sequenced after the gate
so the work is not wasted if Phase 1 fails.

**Phase 3 — roll out to all 20.** One loop in `build.mjs`. A unit test asserts every entry in
`GAME_PAGES` gets a manifest with a distinct `id`, and an e2e asserts each page links exactly one and
that it resolves 200. Cheap, and it makes "someone adds game 21 and forgets" impossible.

**Phase 4 — honesty and offline proof.** An e2e that loads a game, goes offline, and reloads. The
`?r=` share links and how-to pages must survive install (they are same-origin navigations, so
network-first covers them — assert it rather than assume).

**Not in this run:** CSP + SRI injection (croft-pwa does this; whether it travels is an open
question, COHESION §69); adopting relative paths repo-wide; any Emoji Wars / Tier-3 work; a TWA or
any Android packaging — which would make the shelf capture *all* links and is the one choice that
would actively break per-game install.

## Open Questions

**Q1 — app names.** "Solitaire" or "Croft Solitaire"? Home screens truncate hard (~12 chars). Default:
bare game name as `short_name`, `"<Game> · Croft fun"` as `name`.

**Q2 — does the shelf app get a different start_url than `/`?** An installed shelf might prefer to
open on the drawer rather than the marketing top. Default: `/`, unchanged, until someone uses it.

**Q3 — display mode.** `standalone` throughout, or `fullscreen` for games? Default: `standalone`
everywhere — `fullscreen` hides the status bar and the shelf's own chrome expects it. Revisit per
game later if wanted.

None of these blocks Phase 0 or Phase 1.
